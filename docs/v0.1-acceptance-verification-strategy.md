# v0.1 Acceptance and Verification Strategy

## Decision

Nearly Headless CMS v0.1 is accepted through complete traceability from every normative product and architecture decision to observable automated or manual evidence. Source-code coverage percentages do not define acceptance. Every public behavior, invariant, failure, exclusion, compatibility promise, and supported platform has one or more stable acceptance identifiers, while coverage reports remain diagnostic tools.

The strategy combines pure and type-level tests, shared Adapter conformance suites, real-boundary integration and failure tests, complete-system journeys, package compatibility checks, selected visual baselines, WCAG-mapped accessibility evidence, and explicit manual protocols for behavior that Bun WebView cannot establish. Required tests receive no automatic retry or quarantine.

## Acceptance manifest

`acceptance/v0.1.ts` is the typed, machine-checked source of truth. A checked generated view at `docs/acceptance/v0.1.md` makes the same matrix readable without executing TypeScript. The generated view is byte-compared by `check:generated` and is never edited directly.

Each acceptance case records:

- a stable identifier;
- the originating decision and source link;
- one observable claim;
- its verification level;
- owning workspace or cross-system suite;
- command and test selector;
- required runtime, operating system, Adapter, and external process;
- automated or manual status;
- expected evidence artifacts; and
- any explicit limitation that keeps the claim narrower than general compatibility.

Identifiers use durable capability prefixes rather than file names: `DEF`, `FLD`, `ENT`, `QRY`, `REL`, `HIS`, `MIG`, `RTX`, `IDN`, `AUT`, `FSP`, `HTTP`, `GEN`, `CMS`, `BLOG`, `E2E`, `VIS`, `A11Y`, `PKG`, `COMP`, and `ARCH`. Renaming or reorganizing an implementation file never renames an acceptance case.

Every normative sentence in the settled v0.1 decisions maps to at least one case. One case may prove several statements only when they have one indivisible observable outcome. Exclusions receive negative architecture, route, dependency, import, or behavior checks rather than disappearing from the matrix.

## Verification levels

### Pure and type-level verification

`bun:test` covers deterministic computation and state models. Table-driven and deterministically generated cases exercise:

- Content Definition parsing, graph validation, canonical fingerprints, compatibility classification, and Effect Schema compilation;
- every built-in Field Kind, constraint, default, Field Group composition, and Custom Field registration rule;
- generic Entry operations and the complete Entry Query algebra, including text semantics, sorting, projection, pagination, cursor binding, Query Limits, and unsupported capabilities;
- Relationship and Rich Text reference integrity and bounded expansion;
- Entry History, Write Tokens, revision retention, deletion, restoration, and Permanent Purge state transitions;
- migration graph uniqueness, Migration Handler outcomes, preparation and staleness transitions, cutover planning, and restoration through Migration Paths;
- Rich Text structure, normalization, editor transactions, selection models, history coalescing, reference insertion, and unsupported extensions;
- retry classification, form drafts, validation summaries, conflict/reapply behavior, render models, generated-client failure classification, and static Public Blog render models.

Deterministic identifier, Clock, stream, callback, failure, and persistence Adapters make generated examples reproducible. Test seeds are fixed and reported on failure. The suite adds no blanket property-testing dependency merely to rename deterministic generation.

TypeScript 7 compiles positive and negative fixtures for:

- the one public CMS service and every required Effect Layer;
- missing-Layer composition failures;
- every explicit package import path and named module;
- portable versus Bun-only declaration isolation;
- Builder operation declarations, Content Definitions, Entry values, errors, and Adapter interfaces; and
- the absence of default, wildcard, deep, and private imports.

Negative fixtures use compiler assertions such as `@ts-expect-error` only when the rejected program is itself the contract under test. Type tests never weaken the project compiler configuration.

### Adapter conformance suites

Internal reusable conformance suites define the observable contract for:

- Definition Catalog;
- Entry persistence and Query evaluation;
- Asset management and streaming;
- Current Identity;
- Authorization;
- Transport;
- Entry History and retention; and
- definition migration preparation and atomic cutover.

Every applicable shipped Adapter passes the same suite. Each Adapter then adds implementation-specific failure, recovery, capacity, and lifecycle tests. In-memory Adapters cannot substitute for the Filesystem Persistence Layer or real HTTP server where the implementation choice is observable.

The v0.1 package documents the conformance obligations for CMS Builders but does not expand `nearly-headless-cms/testing` into a public general-purpose conformance kit. A future public kit requires a separate package-interface decision.

Arbitrary Builder callbacks cannot be proven pure. Acceptance proves that the library stores no executable code, invokes callbacks only through the declared interface, validates every result, and preserves atomicity on failure. Shipped and Example validators, extensions, operations, and migrations receive repeat-execution determinism tests. Other callback purity and side-effect freedom remain explicit CMS Builder obligations; production code neither sandboxes callbacks nor invokes a mutation twice to guess at purity.

## Definition, persistence, and migration integration

Integration cases compose the public CMS service with the shipped Adapters and prove:

- Catalog history and the active Definition Registry remain distinct, with the Definition Registry library-owned and private;
- complete activation compiles and publishes one snapshot or changes nothing;
- request-held snapshots remain immutable while later activations occur;
- unknown Fields, kinds, formats, extensions, graph cycles, collisions, and fingerprint mismatches fail without changing current state;
- generic Entry mutations atomically validate uniqueness, Assets, Relationships, Rich Text references, history, tokens, and retention;
- all supported Query behavior is identical across conforming persistence Adapters and never approximated;
- reference-blocked deletion hides referrers and generic operations never cascade implicitly;
- migration preparation reads a coherent source generation, becomes stale after a source write, and commits the target snapshot and Entries together only after successful re-preparation; and
- every migration failure class leaves the active snapshot and Entries unchanged.

Versioned fixtures preserve serialized Content Definitions, Rich Text documents, migration graphs, Entry History, and Filesystem Persistence generations. `0.1.0` creates the first compatibility baseline. Every later patch must read and operate on all retained fixtures applicable to its compatibility promise.

## Filesystem Persistence Layer

The filesystem suite uses real fresh temporary roots and deterministic fault injection. It covers:

- empty-root initialization, format markers, incompatible or externally modified roots, and one initialized writer;
- opaque path-safe identifiers and private layout invariants;
- immutable-generation reads and old-or-new visibility for every multi-record mutation;
- every staged write, synchronization, rename, manifest publication, and cleanup failure point;
- `atomic` and `durable` acknowledgement distinctions and durable-capability rejection;
- concurrent reads, serialized writes, source-generation conflicts, retention, reclamation, and protected in-flight streams;
- large, slow, backpressured, cancelled, truncated, corrupt, and digest-mismatched Asset streams;
- permission, capacity, transient I/O, corruption, unsupported capability, and resource-limit classification;
- abandoned staging cleanup, committed-corruption preservation, disposable-index rebuilding, and restart recovery;
- symlink, traversal, path casing, Unicode, reserved-name, and unexpected-directory cases; and
- child-process termination before and after every reader-visible commit boundary.

Exhaustive platform-independent model, failpoint, concurrency, cancellation, and recovery cases run on Linux. The complete real-filesystem conformance suite runs on macOS, Linux, and Windows. Platform-specific durability probes, permissions, symlinks, casing, Unicode, rename behavior, and child-process recovery run on every affected platform.

Process termination proves application crash recovery, not survival of power loss. `durable` acceptance proves that the required synchronization operations are invoked successfully or initialization rejects the policy; it makes no laboratory power-loss claim.

## HTTP, OpenAPI, and Typed Client Bindings

In-memory HTTP contract tests exhaustively cover:

- the separate Management and Headless route catalogs;
- methods, paths, request and response schemas, status codes, headers, media types, direct success bodies, and page shapes;
- Delivery and Management Operation declaration, collision, capability, and activation validation;
- Definition discovery, fingerprints, preconditions, API Contract Versions, Field Kind and Rich Text capability advertisement;
- Current Identity installation and exact Authorization ordering without existence disclosure or bypass;
- Write Token, cursor, request-identifier, idempotency, ETag, and cache semantics;
- every stable error document and safe-detail mapping, using `UnsupportedQueryCapability` as the canonical query failure;
- CORS defaults and configured preflight behavior;
- OpenAPI 3.1 equivalence to the served contract; and
- the absence of unrestricted Headless CRUD, generic queries, documentation UI in the library, or undeclared routes.

Real socket integration tests own behavior an in-memory request cannot prove:

- multipart streaming and validation;
- Asset GET and HEAD, strong ETags, conditionals, exactly one range, and 206/304/416 responses;
- backpressure with slow producers and consumers;
- disconnect and timeout interruption;
- failure before versus after headers begin;
- request and body limits;
- active-request drain, forced interruption, finalization, and server release; and
- public export completion, size rejection before headers, and immutable-generation coherence during concurrent mutation.

Generated bindings pass malformed schema, media, status, interruption, timeout, unsupported-definition, and declared-error fixtures, then invoke a real server. Canonical Management and Headless OpenAPI plus generated app-local source are committed goldens. Intentional changes use explicit generation commands and reviewed diffs; development and builds never regenerate implicitly.

## Example applications

Pure application tests cover form, retry, route, rendering, editor, static-export, Comment, and watcher models. Integration tests prove:

- the Example CMS serves its React application, Management API, Headless API, health route, and protected documentation routes through one Effect/Bun server;
- router loaders, TanStack Query cancellation, native forms, Effect Schema decoding, failure retention, and cache invalidation preserve their settled ownership;
- Bun development and ahead-of-time builds use the selected bundling and Tailwind integration;
- process coordination acquires the CMS, waits for readiness, runs dependents, and finalizes every child on success, failure, timeout, and interruption;
- separate deterministic OpenAPI artifacts generate separate app-local clients;
- the Public Blog imports neither the Example CMS nor the reusable library;
- `astro dev` and `astro build` run through pinned Bun;
- exactly one validated Public Content Export feeds every static page, listing, Asset reference, and RSS result;
- export failure cannot fall back to stale content;
- the development watcher conditionally and atomically replaces a coherent snapshot;
- static output works without JavaScript, has no SPA fallback, and performs no browser-time content queries; and
- Comment progressive enhancement is the only browser content mutation.

A repository-owned architecture check inspects manifests, workspace dependencies, imports, generated files, routes, and configuration. It rejects forbidden cross-application dependencies, a shared SDK, private deep imports, accidental public exports, undeclared workspace dependencies, and the disallowed frameworks, generators, DOM simulators, and browser-test stacks named by the application decision. Astro's transitive use of Vite does not violate the prohibition against adopting Vite for the Example CMS or as a direct Public Blog dependency.

## Complete-system journeys

The complete acceptance coordinator runs real processes, the real HTTP boundary, generated clients, and the Filesystem Persistence Layer. It must:

1. compose and deterministically seed every Example Blog Content Type, status, Relationship, revision, moderation state, Rich Text node, migration path, and public route;
2. create and save a draft Post, inspect its revision, publish it, rebuild, and verify its page, listings, relationships, Assets, and RSS output;
3. submit a Comment with idempotency, prove pending invisibility, approve it, rebuild, and prove public visibility, then exercise the rejected path;
4. produce a stale Write Token conflict, preserve the complete local draft, load current state, and deliberately reapply or discard;
5. restore an earlier revision under current definitions, then exercise confirmed cascade, detachment, deletion, and Permanent Purge behavior;
6. upload and reference an Asset, replace it through the resumable sequence, and verify authorized delivery, ranges, cleanup, and safe failure progress; and
7. activate a Compatible Definition Change, prepare an incompatible migration, stale it with a concurrent write, re-prepare, cut over atomically, and verify old-or-new visibility.

Focused integration tests retain exhaustive failure permutations. End-to-end journeys prove that the deep modules compose; they do not duplicate every lower-level case through the user interface.

## WebView qualification and automated interaction

Before application acceptance relies on experimental Bun WebView, a qualification suite runs ten consecutive times on the pinned macOS runner with zero retry. Each run proves:

- launch and connection;
- navigation and browser-history transitions;
- trusted keyboard input;
- dialogs and focus restoration;
- viewport changes;
- screenshot capture;
- browser-console capture;
- assertion and application-failure reporting; and
- child-process and WebView cleanup.

Any console error, leaked process, unexplained failure, or retry requirement fails qualification and reopens the WebView choice.

Qualified WebView automation covers the critical CMS and Public Blog journeys, semantic DOM and ARIA state, keyboard behavior, dialogs, validation focus, server-failure draft retention, responsive layout, and Comment receipt announcements.

## Visual verification

Normative automated viewports are:

- `390x844` for narrow phone presentation;
- `768x1024` for intermediate and stacked presentation; and
- `1440x1000` for wide desktop authoring.

Selected committed baselines cover the CMS overview, Post editor, validation, conflict, history, moderation queue, Public Blog home and Post pages, and Comment success and failure states. Content, identifiers, clocks, build identity, animation, and other volatile values are deterministic.

The pinned macOS, WebKit, and font environment uses pixel-exact comparison. An intentional baseline change requires a reviewed diff and explicit update command. A runner-image change creates a deliberate baseline migration rather than silently adding tolerance. Narrow CMS acceptance covers reading and basic management, not mobile or touch Rich Text authoring.

## Accessibility and manual protocols

The implemented CMS and Public Blog flows target applicable WCAG 2.2 AA criteria without claiming formal third-party certification. The acceptance manifest maps every applicable criterion to automated, manual, or combined evidence.

An exact-pinned `axe-core` development dependency runs inside the real WebView pages. Every applicable reported violation fails acceptance, and every incomplete result receives documented human resolution. Automated checks additionally assert landmarks, headings, names, descriptions, ARIA state, keyboard order, focus visibility and restoration, contrast, validation summaries and linked errors, and live status announcements.

A versioned release-candidate checklist on the pinned macOS environment records the candidate commit, operating-system, browser, assistive-technology and IME versions, reviewer, date, steps, and findings. It covers:

- keyboard-only completion of critical CMS and Public Blog flows;
- VoiceOver landmarks, navigation, headings, controls, dialogs, focus, validation, Rich Text toolbar state, and Comment receipt announcements;
- Japanese Hiragana IME composition through insertion, editing, block splitting, undo and redo, save, and reload;
- native drag selection and real clipboard copy and paste into Rich Text, including plain-text-only import;
- narrow-viewport CMS reading and basic management; and
- destructive-action language and treatment for deletion, cascade, Asset replacement, and Permanent Purge.

Current stable Safari, Chrome, and Firefox on macOS receive manual critical-flow smoke coverage. Static Public Blog content and navigation are checked with JavaScript disabled. Comment enhancement, CMS authoring, and a focused Rich Text edit and save are checked with JavaScript enabled. Evidence records exact browser versions; v0.1 makes no claim for untested versions, mobile or touch authoring, or other desktop operating systems.

A failed WebView, Rich Text, VoiceOver, IME, clipboard, selection, browser, or accessibility gate reopens its originating decision. Required behavior cannot be silently removed and the gate cannot be waived while retaining the corresponding claim.

## Package and compatibility verification

The package-specific release gates from the npm Package and Release-Readiness Contract remain mandatory and use the one `bun pm pack` archive throughout inspection, clean-consumer tests, runtime smoke tests, dry-run, and protected publication.

Two clean builds must produce byte-for-byte equal `dist/` files and semantically equal inspected archive entries, modes, sizes, and contents. Whole gzip checksums need not match across independent builds unless Bun's container metadata is itself deterministic. The release builds one authoritative archive once and preserves that archive's checksum through the workflow.

`0.1.0` records the initial declarations, export map, consumer programs, wire artifacts, serialized values, and persisted filesystem fixtures. A later patch:

- compares public exports and declarations;
- compiles and executes prior consumer programs;
- reads every retained persisted fixture;
- preserves prior wire and error contracts; and
- executes the current implementation against applicable previous-version fixtures.

Pull requests test the minimum, locked, and latest-known compatible Effect versions. Scheduled and release suites enumerate every currently published Effect version in the declared peer range. Bun runs at the declared minimum and pinned current supported release. Node runs at the minimum supported major and every active supported LTS major. A failure caused by a newly published dependency or runtime opens a blocking compatibility issue and never silently changes the package promise.

The release workflow is verified without publishing a disposable package. Static workflow and least-privilege checks, command tests, exact-tarball dry runs, protected-environment configuration review, and a tabletop bootstrap/OIDC exercise establish readiness. Actual first-package trusted-publisher setup, bootstrap-token revocation, provenance, registry installation, and post-publication verification remain runbook steps after the authorized first publication.

## Non-functional evidence

v0.1 sets no universal latency, throughput, or fixed-memory service-level objective. Acceptance proves semantic resource limits, bounded work, bounded history and export behavior, backpressure, configured timeouts, bounded drain, and refusal to approximate. Controlled clocks, instrumented streams, counters, and hard test configurations establish those properties deterministically. Benchmarks may publish informational baselines but do not block acceptance unless a settled resource bound is violated.

## Commands and CI cadence

The root `bun run acceptance` command coordinates these independently runnable commands:

- `verify`;
- `check:architecture`;
- `check:generated`;
- `test:unit`;
- `test:types`;
- `test:contract`;
- `test:integration`;
- `test:filesystem`;
- `test:webview`;
- `test:visual`;
- `package:inspect`; and
- `package:smoke`.

Workspaces own their development, build, test, and start commands. The root coordinates repository-wide evidence without creating another runtime or test-support workspace.

CI uses four lanes:

1. **Pull request**: lint, type checks, unit and in-memory contract suites, generated and architecture checks, package build and smoke, application builds, and focused integration cases.
2. **Main**: real HTTP and process integration, Astro development and build, and macOS WebView smoke journeys.
3. **Scheduled**: exhaustive fault injection, every published compatible Effect version, repeated flake detection, and the complete operating-system matrix.
4. **Release tag**: every mandatory automated check rerun from one frozen clean installation and candidate commit. Scheduled results never substitute for release evidence.

Required suites receive zero automatic retries. A diagnostic rerun may collect information but cannot change the recorded result. A flaky required case blocks its lane until fixed or until the owning product decision is explicitly reopened; quarantine never counts as acceptance.

## Evidence bundle

Every CI acceptance run uploads an immutable evidence bundle containing:

- candidate commit and acceptance-manifest version;
- Bun, Node, npm, TypeScript, Effect, operating-system, browser, WebView, Astro, and relevant dependency versions;
- invoked commands and selected cases;
- machine-readable results and logs;
- generated and architecture check reports;
- filesystem failpoint and recovery reports;
- screenshots and visual diffs;
- accessibility reports;
- package inspection JSON, archive checksum, and dry-run report; and
- links to separately recorded manual evidence when applicable.

Run evidence is retained by CI rather than committed. Versioned inputs, compatibility fixtures, and approved goldens are committed.

## Acceptance exit condition

The v0.1 implementation is accepted as ready for an intentional release only when:

- every acceptance-manifest entry has its required evidence;
- every automated case is green from the same candidate commit and frozen dependency state;
- every required platform matrix completes;
- no required result depends on a retry, quarantine, or unexplained failure;
- every intentional fixture or golden change is explicitly reviewed;
- every manual gate is completed against that candidate;
- no open issue demonstrates a violation of a normative v0.1 contract;
- package inspection, clean-consumer smoke, and npm dry-run succeed; and
- the generated acceptance report receives maintainer sign-off.

The preserved prototypes demonstrate design coherence but are not implementation acceptance evidence. Actual npm publication remains outside this acceptance decision.

## Consequences

- Acceptance measures promised behavior rather than incidental implementation structure or an arbitrary coverage percentage.
- Shared conformance suites make the Builder Layer seams real and prevent shipped Adapters from drifting semantically.
- Real filesystems, sockets, processes, and browsers are used only where their behavior is part of the contract, keeping most feedback deterministic and fast.
- Complete-system journeys remain few and valuable because lower suites own combinatorial failures.
- Experimental WebView and app-owned Rich Text choices carry explicit qualification and manual evidence rather than hidden confidence gaps.
- Zero retries and full decision traceability make acceptance failures expensive but trustworthy.
