# Headless Transport and Typed-Client Contract

## Decision

One required transport may host two explicit, versioned HTTP contract groups. The Management API exposes configured authoring, definition-lifecycle, history, Asset, and other management capabilities to a CMS user interface. The narrower Headless API exposes only named CMS Builder-defined Delivery Queries and Delivery Commands to Content Clients. It never exposes unrestricted generic CRUD or Entry Query behavior. A Delivery Query fixes public-selection rules such as published status in its handler; a Delivery Command accepts only caller-owned values and assigns protected values, such as Comment status and creation time, internally.

The separately importable HTTP Transport uses Effect v4 `HttpApi` declarations to implement ordinary resource-oriented HTTP with JSON-compatible schemas, OpenAPI, multipart input, streamed Asset responses, and in-memory contract testing. Effect RPC is not the public protocol. The two groups use explicit major URL versions, initially `/api/v1/management` and `/api/v1/headless`. Breaking HTTP changes introduce a new major route group that may run beside the old group. Additive optional fields and endpoints may evolve compatibly within one major version. This API Contract Version is independent of Content Definition revisions.

OpenAPI describes stable route, parameter, success, and error shapes. Runtime definition discovery separately returns the active Definition Snapshot fingerprint, API Contract Version, serializable definitions, supported Field Kind versions and capabilities, and Rich Text extension versions. Headless discovery exposes only the Public Definition Snapshot reachable through its public operations. Management discovery may expose the complete active Definition Snapshot and lifecycle operations. Neither surface exposes executable validators or compiled Effect Schemas.

Headless discovery includes the API contract major version; active Definition Snapshot identifier and fingerprint; definition and compiler format versions; public Content Type and Field Group definitions; Field Kind identifiers, versions, and capabilities; Rich Text document format, core vocabulary version, and public extensions; Delivery Operation identifiers, methods, paths, reachable Content Types, and idempotency requirements; Asset Delivery URL template and capabilities; and the OpenAPI document URL. The server does not tailor discovery to claimed client support. A client compares advertised versions with its runtime decoders and fails explicitly when it cannot support a Field Kind or Rich Text extension.

Delivery Operations are declared at CMS composition time with a stable identifier, HTTP method and path, request and response schemas, reachable Content Types, and CMS Builder handler. Their route set and OpenAPI contract remain fixed until the CMS is recomposed and redeployed. Activating a Definition Snapshot may change runtime content shapes and discovery data but cannot add, remove, or rename a Delivery Operation.

Definition activation revalidates every composed operation's declared Content Types, projections, Field paths, Field Kind versions, and Rich Text extensions. It fails atomically when the target snapshot would violate a request or response contract. Compatible additions update discovery and its fingerprint. Removing or incompatibly changing a publicly required value requires a newly deployed operation or API major version before that snapshot can activate.

CMS-specific authoring workflows use composition-time Management Operation declarations with stable identifiers, methods and paths, request and response schemas, capability dependencies, middleware, and handlers. They appear in Management OpenAPI and generated bindings. The Example CMS declares operations for Post publication and return to draft, Comment approval and rejection, confirmed cascade deletion, Category and Tag detachment, and image replacement. Their handlers invoke ordinary authorized CMS operations without a privileged bypass.

Both API groups use lowercase plural resource paths, opaque identifiers in path segments, and `lowerCamelCase` JSON properties. Simple resource operations use ordinary HTTP methods; complete Entry replacement uses `PUT`, and the generic transport has no `PATCH`. Recursive Entry Queries use `POST` to a subordinate `query` route. Builder-selected Delivery paths live below the versioned Headless API prefix and are rejected at composition time when their paths, stable operation identifiers, or reserved prefixes collide.

Management resources are scoped below `/api/v1/management/definition-spaces/{definitionSpaceId}`. Predictable subordinate collections cover Content Type Entries and queries, Entry state and revisions, Assets and Asset content, definitions and Definition Snapshots, Catalog events, Migration Manifests, and Migration Preparations. Restore, Permanent Purge, retirement, preparation, and cutover use named subordinate `POST` resources instead of overloaded query parameters.

JSON request and response bodies use UTF-8 `application/json` and preserve the distinction between an absent property and explicit `null`. Dates and datetimes use their defined ISO encodings, integer Fields are restricted to JSON-safe integers, and numbers must be finite. IDs, fingerprints, cursors, Write Tokens, and idempotency keys are opaque strings. Entry values are objects keyed by Field Key. Asset bytes are streamed using their media type and are never embedded as base64 JSON.

The transport resolves request-scoped Current Identity for both API groups. A Management endpoint invokes the corresponding public generic CMS operation, which performs its required Authorization check exactly once. A Delivery Operation invokes the same public CMS operations from its handler; every invoked operation authorizes normally, and the transport has no privileged bypass. Additional policy specific to a Delivery Operation belongs to CMS Builder middleware or its handler. An expanded generic read first authorizes its base read Action and then authorizes one Relationship Expansion Action covering the root Resource and complete requested expansion plan. Both checks precede validation and lookup, and a denial does not reveal whether any root or target exists.

Definition-dependent responses identify the Definition Snapshot fingerprint used to produce them. A client may pin subsequent requests to an expected active fingerprint. A mismatch returns HTTP 412 and never serves a historical snapshot. Static generation discovers and pins one fingerprint for a build, restarting cleanly if the active snapshot changes. Cursors remain bound to their originating query and snapshot; incompatible reuse returns `Conflict`.

Cross-cutting headers are `X-Request-Id`, `CMS-Definition-Fingerprint`, `CMS-Expected-Definition-Fingerprint`, `CMS-Write-Token`, and the standard `Idempotency-Key`. A valid request identifier from trusted ingress may be retained; otherwise the transport generates one and always returns it. Standard `ETag`, `If-None-Match`, `Range`, and `If-Range` apply only to immutable Asset bytes and completed export artifacts rather than Entry concurrency.

A Typed Client Binding is app-local generated source, not a shared runtime SDK dependency. It types stable HTTP operations and discovery data while runtime Entry values are decoded against serializable definition data. The Public Blog imports neither the Headless CMS implementation nor the reusable library and SDK.

Generic Management operations use dynamic Entry Representations decoded against discovery. A Delivery Operation may instead return either a dynamic public Entry projection or a CMS Builder-defined static data-transfer schema. The Example Headless API uses stable public schemas such as `PublicPost`, `PublicAuthor`, and `CommentReceipt`, while Rich Text and extensible Field values nested inside them still use discovery-driven runtime decoding.

The composed CMS serves separate canonical OpenAPI 3.1 documents for Management and Headless contracts and reproducibly exports the same artifacts during development. Headless OpenAPI is public at a stable route; Management OpenAPI passes through the same Management identity and middleware as its endpoints. Stable operation identifiers drive generated method names. The reusable library supplies no documentation user interface. A generic generator produces app-local transport bindings from the Headless artifact; selection of the generator belongs to the application-stack decision. Runtime definition discovery drives decoding of dynamic Entry values, so a compatible Definition Snapshot activation does not require regenerating the client.

Typed Client Bindings preserve separate failures for declared API errors, connection/interruption/timeout `TransportFailure`, unexpected status/media/malformed-body `ProtocolFailure`, and local `UnsupportedDefinition` when a decoder cannot support an advertised Field Kind or Rich Text extension. They never collapse all failures into one generic exception.

Expected failures use a stable tagged JSON representation with a machine-readable code, safe message, request correlation identifier, and structured safe details. `InvalidInput` maps to HTTP 400, `Forbidden` to 403, `NotFound` to 404, conflicts including stale cursors and reference-blocked deletion to 409, `UnsupportedCapability` to 422, retryable infrastructure failure to 503, and unexpected defects to 500. Validation details use stable Field paths and reason codes. Transport errors never reveal adapter causes, filesystem paths, blocked referrers, or existence hidden by authorization.

The JSON error document has stable `code`, `message`, and `requestId` properties plus optional safe `details`. Validation details contain `issues` whose `path` is an array of unambiguous segments and whose `reason` is a stable machine value. Unexpected defects use `InternalError` and reveal only their request identifier; a retryable 503 may carry `Retry-After`.

Successful endpoints return their direct typed representation rather than a universal data envelope. Query pages use an `items` array and optional `nextCursor`; deletions and other bodyless success may use HTTP 204. Cross-cutting request identifiers and Definition Snapshot fingerprints use response headers. Discovery has its own explicit document shape.

An Asset ID is not an access capability. A Headless API that returns Asset or Rich Text references may declare one canonical Asset Delivery Operation and advertise its URL template through discovery. The CMS Builder handler applies delivery-specific policy, such as requiring the Asset to be reachable from published content, before invoking the ordinary authorized Asset read. The Example CMS exposes only Assets reachable from public Posts, Authors, Categories, or Tags rather than every uploaded draft Asset.

The reusable transport does not promise automatic mutation deduplication. Each Delivery Command declares whether it requires an opaque idempotency key, and the CMS Builder handler owns any durable result storage and replay behavior. The Example Blog's Comment-submission command requires a client-generated key and persists builder-owned deduplication data. Generic Management creates and uploads are not automatically retry-safe; a `PUT` replacement is repeatable only while its concurrency preconditions still hold.

Entry-only Example Management commands commit their complete cascade or detachment atomically within Entry persistence. Cross-service image replacement is instead a resumable sequence: ingest the new Asset, atomically reassign Entries, then delete the old Asset. It never removes the old Asset before reassignment succeeds. A command key makes retries return the same structured progress or result; a failed attempt may leave a safe unreferenced new Asset that can be reused or explicitly deleted.

The HTTP adapter configures limits for headers, URL length, JSON bodies, multipart metadata and files, and request duration. It maps those transport failures to stable 413, 414, 431, and 408 responses, interrupts the running Effect after client disconnection or timeout, preserves streaming backpressure, and cleans abandoned upload staging through `Scope`. CMS Query Limits remain domain failures. Anonymous rate limiting and HTTP 429 belong to deployment middleware.

Discovery uses its Definition fingerprint as an ETag and `Cache-Control: no-cache` so clients can revalidate conditionally. Management JSON and error responses use `no-store`. Headless reads default to `no-cache` unless their Delivery Operation declares an explicit safe policy; Comment submission and its receipt use `no-store`. Identity-dependent responses set appropriate `Vary` headers and cannot accidentally become shared public cache entries.

Scoped Transport shutdown stops accepting new connections, gives active requests and streams a configured bounded drain period, interrupts remaining work when that period expires, runs finalizers for handlers, upload staging, and protected Asset generations, and completes server cleanup before releasing the Transport Layer. Forced shutdown interruption is lifecycle behavior rather than a CMS-domain error response.

CMS Builder middleware owns authentication and produces Current Identity. CORS is disabled by default and, when enabled, names explicit origins, methods, and headers. Cookie-based Management identity requires builder-provided CSRF protection. TLS termination, trusted-proxy handling, rate limiting, and security headers belong to deployment middleware. The transport never infers identity from an untrusted header. The Example CMS remains intentionally open-access; a separately hosted Public Blog deployment enables only the required cross-origin Comment flow.

Ordinary success uses HTTP 200, immutable-resource creation uses 201, and bodyless deletion uses 204. Conditional Asset and export reads use 304; Asset ranges use 206 or 416. Request or domain decoding uses 400, unsupported methods 405, unacceptable response media 406, timeout 408, Definition precondition mismatch 412, body or URL limits 413 and 414, unsupported request media 415, and header limits 431. The contract uses 202 only for a genuinely asynchronous future operation.

A generic Entry update is a complete replacement. Partial mutations require a separately named CMS Builder command and are not alternate semantics for the generic update operation.

The Management API has standard resource groups for the settled generic capabilities. Entries expose create, projected get, complete replacement, delete, and query. History-enabled Content Types additionally expose current state, revision listing, revision inspection, restore, and Permanent Purge. Assets expose ingestion, metadata read, byte read, and delete, but no generic metadata update, replacement, or list operation in v0.1. Definition lifecycle exposes revision append, active-snapshot inspection, paginated Catalog reads, retirement, and activation. Migration lifecycle exposes Manifest append, preparation, report inspection, and Atomic Definition Cutover. Executable Migration Handlers are registered only at CMS composition and never cross HTTP. A Compatible Definition Change may activate directly; a representation-changing activation references a successful non-stale Migration Preparation.

Ordinary Entry get and query responses never contain Write Tokens. A dedicated current-state endpoint returns the complete Entry and opaque Write Token. History-enabled create, replacement, and restore return both values. Replacement and deletion receive the current token through `CMS-Write-Token`; restore and Permanent Purge carry it in their structured command bodies. Non-history mutations return an ordinary Entry Representation or a bodyless success. The contract explicitly distinguishes history-enabled and ordinary outcomes without treating a Write Token as an HTTP ETag.

The Example Headless API declares Delivery Operations to discover its public snapshot, list published Posts newest-first, resolve one published Post by slug, resolve public Authors, Categories, and Tags by slug, list their published Posts, list approved Comments for a published Post, submit a pending Comment with an idempotency key, resolve a public-safe Rich Text Entry reference, and deliver an authorized Asset. It exposes no draft Post, pending or rejected Comment, arbitrary Entry Query, or visitor update and delete operation.

The Example paths are `/schema`, `/posts`, `/posts/{slug}`, `/authors/{slug}`, `/categories/{slug}`, `/tags/{slug}`, subordinate Post listings for each taxonomy or Author, `/posts/{postId}/comments`, `/references/entries/{entryId}`, `/assets/{assetId}`, and `/export`, all below `/api/v1/headless`. A draft Post, unapproved Comment, inaccessible Rich Text reference, or unauthorized Asset returns the same `NotFound` representation as an absent resource. Delivery-specific public reachability is checked before an ordinary generic read.

Public listings use `pageSize` and opaque `cursor` query parameters. Published Posts sort by publication time descending and Entry ID; Author, Category, and Tag Post listings use the same order. Approved Comments sort by creation time ascending and Entry ID. Slugs are CMS Builder-validated lowercase URL-safe values unique within their Content Type. Route matching percent-decodes them without case folding or normalization. Invalid, stale, or mismatched cursors never restart silently.

Successful Comment submission returns HTTP 201 with only an opaque `submissionId` and the public status `pending`; it exposes no moderation URL or submitted body. Reusing its idempotency key with the same canonical input returns the original receipt. Reuse with different input returns `IdempotencyConflict`. The deduplication record remains for the retained lifetime of the Comment, including after rejection.

The Rich Text Entry-reference resolver returns the target Entry ID, Content Type identifier, and a CMS Builder-declared public Field projection. It is limited to eligible target Content Types and Entries reachable from public Rich Text, returning `NotFound` otherwise. It does not return a Public Blog URL; the Content Client derives presentation routes from public values such as slug.

The Example API also declares an `exportPublicBlog` Public Content Export. It evaluates one immutable persistence generation and streams or returns the complete bounded public dataset needed for static pages and the RSS feed. Static generation uses this export, then fetches immutable Assets separately. Interactive paginated endpoints retain best-effort cursor continuation rather than cross-request Entry snapshots.

`exportPublicBlog` first produces one bounded, validated JSON document containing its Definition fingerprint and public Posts, Authors, Categories, Tags, approved Comments, and referenced Asset metadata. Only after completion does the server stream the artifact with a strong ETag. Exceeding the configured export-byte bound returns `ExportTooLarge` before headers begin.

The Asset Delivery Operation supports `GET` and `HEAD`, validated stored media type and byte length, a strong digest-derived ETag, `If-None-Match`, `If-Range`, and one byte range per request. It returns 206 or 416 as appropriate, advertises `Accept-Ranges: bytes`, uses CMS Builder-configured `Cache-Control`, and sends `Content-Disposition: inline` with a safely encoded original filename when available. Policy, metadata lookup, conditional evaluation, and range validation complete before response headers begin. A corruption or I/O failure discovered after streaming starts aborts the stream because it can no longer become a typed JSON response.

Management Asset ingestion uses streaming multipart input containing exactly one JSON `metadata` part and one binary `content` part. The client supplies neither Asset ID nor digest. The Asset service validates metadata, claimed media type, and image dimensions while the adapter computes the digest and enforces byte limits with scoped staging cleanup. Missing, duplicate, or unexpected parts fail. Success returns HTTP 201 with the generated Asset ID, immutable metadata, digest, and byte length.
